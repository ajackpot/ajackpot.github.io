# 화면 문구 작성 가이드

부제: WCAG 2.2의 이해 가능성 원칙과 한국형 웹 접근성 용어를 반영한 테스트 화면 문구 기준

## 1. 목적

이 프로젝트의 화면 문구는 사용자가 테스트 흐름을 쉽게 이해하고, 필요한 행동을 스스로 선택할 수 있도록 돕는다. 친근한 문체를 만들기 위해 장식적인 표현을 늘리기보다 다음을 우선한다.

1. 익숙하고 구체적인 말을 쓴다.
2. 한 문장에는 한 가지 내용만 담는다.
3. 여러 단계는 번호 목록으로 나눈다.
4. 상태나 오류를 알릴 때는 일어난 일과 다음 행동을 함께 말한다.
5. 사용자를 탓하거나 평가하는 표현을 쓰지 않는다.
6. 과업 수행 중에는 성공 여부나 해결 방법을 암시하지 않는다.

## 2. 적용 근거

### 2.1 접근성 기준과 보조 지침

- WCAG 2.2 SC 3.1.3에 따라 낯설거나 제한된 의미로 쓰는 전문 용어에는 뜻을 알 수 있는 방법을 제공한다.
- W3C 인지 접근성 지침은 쉬운 단어, 짧은 문장, 짧은 글 묶음, 분명한 단계 구분을 권장한다.
- W3C 알림 지침은 상태 변화와 오류를 명확하게 알리고, 사용자가 무엇을 할 수 있는지 알려 주도록 권장한다.
- 오류 문구는 기술 원인보다 사용자가 이해할 수 있는 상황과 다음 행동을 먼저 제시한다.

### 2.2 한국어 문체

- 사용자 화면에서는 `~합니다`, `~할 수 있습니다`, `~하세요`, `~해 주세요`를 상황에 맞게 쓴다.
- 필수 행동은 버튼 이름을 그대로 말해 모호함을 줄인다.
- 같은 기능은 모든 서비스에서 같은 이름으로 부른다.
- 영어 약어와 내부 개발 용어는 꼭 필요할 때만 쓴다.

## 3. 기본 작성 원칙

### 3.1 명확하고 짧게 쓰기

- 문단 첫 문장에서 목적을 알린다.
- 긴 문장은 둘 이상으로 나눈다.
- 한 문장 안에 조건과 예외가 많으면 번호 목록이나 별도 문장으로 나눈다.
- `해당`, `관련`, `진행`, `처리`처럼 대상을 숨기는 말보다 실제 대상과 동작을 쓴다.
- 버튼과 링크는 실행 결과가 드러나게 쓴다.

예:

- `예약 캘린더 테스트 시작`
- `새 탭에서 과업 수행 페이지 열기` 또는 `과업 수행 페이지 열기(새 탭)`
- `현재 예약 취소`
- `검색 조건 적용`
- `결과 파일 내려받기`

### 3.2 친근하고 존중하는 문체

- 차분하고 직접적으로 말한다.
- `잘하셨습니다`, `앗`, `이런`, `걱정하지 마세요`처럼 상황과 관계없는 감탄이나 과한 격려는 쓰지 않는다.
- 사용자가 과업을 마치지 못했을 때 `실패`, `불가능`, `잘못함`으로 사람을 평가하지 않는다.
- 결과는 `완료한 과업`, `완료하지 못한 과업`처럼 기록 상태로 표현한다.
- 오류나 중단은 서비스 또는 기록 상태를 주어로 설명한다.

예:

- 지양: `수행에 실패했습니다.`
- 권장: `요청한 자료를 저장한 기록이 없습니다.`
- 지양: `잘못된 시간을 선택했습니다.`
- 권장: `요청한 시간 대신 다른 일정이 예약되었습니다.`

### 3.3 상태와 오류 문구

상태와 오류 문구는 가능한 한 다음 순서를 따른다.

1. 무엇이 일어났는지 말한다.
2. 사용자가 할 수 있는 다음 행동을 말한다.
3. 내부 오류 코드나 구현 원인은 노출하지 않는다.

예:

- `새 탭이 열리지 않았습니다. 브라우저에서 이 사이트의 팝업을 허용한 뒤 다시 열어 주세요.`
- `과업 수행 페이지가 닫혔습니다. 계속하려면 아래 버튼으로 다시 열어 주세요.`
- `과업을 시작하는 데 필요한 정보를 찾지 못했습니다. 이 탭을 닫고, 과업 요청이 있는 창에서 다시 열어 주세요.`

화면낭독기가 같은 내용을 여러 번 읽지 않도록 제목, 본문, 버튼에서 같은 문장을 반복하지 않는다.

### 3.4 테스트 결과에 영향을 주지 않기

- 과업 수행 전과 수행 중에는 어느 화면이 개선안인지 말하지 않는다.
- 정답, 예상 시간, 목표 조작 수, 권장 탐색 순서를 알려 주지 않는다.
- 실제 서비스 피드백은 사실만 알리고 과업 성공 여부는 말하지 않는다.
- 칭찬, 압박, 긴급함을 유도하는 표현을 넣지 않는다.
- 사용자가 과업을 완료하기 어렵다면 현재 상태를 저장하고 다음 단계로 갈 수 있음을 중립적으로 안내한다.

### 3.5 지양하는 표현

- 화면 이해에 필요하지 않은 영어 표현과 약어
- `세션`, `브리지`, `스냅샷`, `실행 ID`, `계측` 같은 내부 용어
- `오류 0x...`, `잘못된 입력`, `사용자가 실패함`처럼 원인을 사용자에게 돌리는 표현
- 같은 안내를 제목·설명·상태 메시지에서 반복하는 문구
- 사전 예상 시간이나 개선폭을 과업 전에 보여 주는 문구

## 4. 현재 화면 용어

| 내부 또는 기술 용어 | 사용자 화면에 쓰는 말 | 설명 |
|---|---|---|
| slot | 예약 시간 / 예약 가능한 시간 | 예약할 수 있는 시간 한 칸 |
| skip link | 결과로 바로 이동 | 긴 반복 영역을 건너뛰는 링크 |
| modal dialog | 대화상자 / 확인 창 | 확인이나 선택을 위해 잠깐 열리는 창 |
| focus | 초점 | 키보드로 현재 선택된 위치 |
| benchmark | 사전 예상 기준 | 실제 수행 전에 계산한 예상 조작 부담. 과업 수행 전에는 표시하지 않음 |
| wrong selection | 목표와 다른 선택 | 요청한 대상이 아닌 곳에서 선택한 횟수 |
| context reset | 위치 다시 찾기 | 작업 뒤 원래 위치로 돌아가지 못해 다시 찾은 횟수 |
| modal escape | 대화상자 바깥으로 초점 이탈 | 대화상자가 열린 동안 초점이 바깥으로 빠진 경우 |
| pointer activation | 클릭 입력 | 마우스나 유사 클릭 입력 |
| task end | 과업 종료 | 현재 기록을 저장하고 과업을 마치는 동작 |
| incomplete / unable | 완료하지 못한 과업 | 요청한 동작을 끝내지 못한 상태로 저장된 기록 |
| hidden duration | 수행 페이지가 보이지 않았던 시간 | 다른 탭을 보거나 페이지가 가려져 결과 시간에서 제외한 시간 |
| reply | 답글 | 기존 댓글 아래에 이어지는 댓글 |
| toast | 화면 하단 상태 안내 | 잠시 표시되며 화면낭독기에도 전달되는 상태 메시지 |
| preview | 미리보기 | 자료를 열기 전에 핵심 내용을 확인하는 창 |
| JSON | 결과 파일 형식 | 수행 기록을 텍스트로 저장하는 파일 형식 |

## 5. 화면별 규칙

### 5.1 홈 화면

- 제목과 첫 문장에서 무엇을 고르는 화면인지 알 수 있게 한다.
- 공개 서비스는 `예약 캘린더`, `댓글 목록`, `검색 결과 목록` 3개만 표시한다.
- 서비스 버튼은 `예약 캘린더 테스트 시작`처럼 대상과 행동을 함께 쓴다.
- 진행 상태는 `수행 전`, `진행 중`, `수행 완료`로 일관되게 표시한다.
- 설문 안내는 세 서비스를 모두 마치면 수행 기록이 자동 입력된다는 내용만 짧게 알린다.

### 5.2 서비스 소개 화면

- 첫 문단에서 사용자가 하게 될 일을 한두 문장으로 설명한다.
- 진행 단계는 번호 목록으로 나눈다.
- `진행 순서`, `알아두세요`처럼 짧고 구체적인 제목을 쓴다.
- 시작 버튼은 `첫 과업 준비하기`, 돌아가기 버튼은 `다른 서비스 고르기`로 쓴다.
- 어느 화면이 더 낫거나 오래 걸릴지 미리 말하지 않는다.

### 5.3 과업 준비 화면

- `이번 요청`에는 목표 상황만 간단히 적는다.
- 버튼 이름, 탐색 순서, 특정 키 사용법처럼 해결 전략이 될 수 있는 내용은 적지 않는다.
- 과업 종료 방법은 테스트 운영에 필요하므로 단계별로 안내한다.
- `과업 요청을 수행 페이지에도 표시` 스위치를 켜면 새 탭 위쪽에도 요청이 보인다고 설명한다.
- 수행 기록이 언제 시작되는지 한 문장으로 알린다.

### 5.4 과업 수행 페이지

- 서비스 콘텐츠와 맨 아래의 이동·종료 영역만 둔다.
- 비교안 설명, 테스트 목적, 예상 시간, 개선 목표는 넣지 않는다.
- 상태 메시지는 실제 서비스에서 자연스럽게 나올 법한 표현으로 제공한다.
- 수행 중에는 정답이나 성공 여부를 말하지 않는다.
- 구현 범위가 큰 기능은 `현재 준비 중`이라고 알리고, 사용할 수 있는 다음 기능을 함께 안내한다.
- 하단 이동 및 종료 버튼과 종료 확인 창의 조작은 결과 지표에 포함하지 않는다.

### 5.5 결과 화면

- `수행 시간`, `총 키 입력`, `초점 이동`, `위치 다시 찾기`, `완료한 과업`, `완료하지 못한 과업`, `사전 예상 기준`처럼 일관된 이름을 쓴다.
- 과업을 끝내지 못한 기록도 `과업 수행 기록` 화면에서 사실대로 설명한다. 성공을 전제로 한 제목을 쓰지 않는다.
- 두 화면의 결과를 비교하는 제목은 `비교안 A와 B 결과 비교`처럼 읽기 쉽게 쓴다.
- 결과 파일 설명은 파일을 언제, 왜 내려받는지 먼저 말하고 형식 설명은 뒤에 둔다.

## 6. 용어 설명 제공 방식

낯선 용어는 별도 용어 카드에 몰아넣기보다 다음 순서로 처리한다.

1. 먼저 쉬운 말로 바꾼다.
2. 꼭 필요한 용어는 처음 나오는 위치에서 짧게 설명한다.
3. 결과 화면의 지표처럼 반복되는 용어는 같은 이름을 유지한다.
4. 개발자용 상세 정의는 화면이 아니라 문서에 둔다.

## 7. 배포 전 문구 점검

- 제목만 읽어도 현재 화면의 목적을 알 수 있는가?
- 각 문장은 한 가지 내용만 전달하는가?
- 여러 단계가 번호 목록으로 나뉘어 있는가?
- 버튼과 링크 문구만 읽어도 결과를 예상할 수 있는가?
- 상태 또는 오류 문구에 일어난 일과 다음 행동이 함께 있는가?
- 사용자를 탓하거나 과하게 격려하는 문구가 없는가?
- 같은 안내가 화면낭독기에서 반복될 가능성이 없는가?
- 과업 수행 전에 해결 전략이나 예상 결과를 노출하지 않았는가?
- 서비스 3곳에서 같은 기능을 같은 이름으로 부르는가?

|---|---|---|
| 검색 기록 | 사용자가 최근에 입력하거나 열어 본 검색어와 자료 기록입니다. | `history`만 쓰지 않는다. |

| 용어 | 설명 | 사용 기준 |

| 한 주 최대 예약 | 같은 주에 예약할 수 있는 횟수 제한입니다. | 제한 안내는 실제 서비스 정책처럼 표현하고, 성공·실패 힌트로 쓰지 않는다. |
| 저장 옵션 | 자료를 개인 보관함·공유 보관함·PDF 파일·텍스트 파일 중 어디에 둘지와 어떤 내용을 포함할지 정하는 선택값입니다. | `save settings` 같은 영어 대신 저장 위치, 포함할 내용처럼 실제 화면 용어로 쓴다. |
| 검색 조건 설정으로 바로가기 | 검색 조건 영역으로 초점을 옮기는 링크입니다. | 단일 페이지 안에서도 긴 조건·결과 영역을 건너뛰는 목적을 드러내기 위해 쓴다. |
| 답변 제출하고 과업 종료하기 | 답변 선택이 필요한 과업에서 답변 제출과 종료를 한 번에 처리하는 버튼입니다. | 별도 제출 버튼을 반복하지 않고, 하단 운영 영역에서 한 번에 처리한다. |
