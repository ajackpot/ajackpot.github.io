# 30단계: 친근하고 명확한 화면 문구 개선 보고서

## 1. 작업 목적

이번 단계에서는 테스트 페이지의 안내, 상태, 오류, 완료, 결과 문구를 전반적으로 다시 검토했다. 목표는 말을 장식하거나 지나치게 다정하게 만드는 것이 아니라, 사용자가 현재 상황과 다음 행동을 부담 없이 이해할 수 있도록 문장을 짧고 차분하게 정리하는 것이다.

다음 원칙을 함께 지켰다.

1. 사용자가 해야 할 일을 먼저 알린다.
2. 여러 행동은 번호 목록으로 나눈다.
3. 상태와 오류는 일어난 일과 다음 행동을 함께 설명한다.
4. 사용자를 탓하거나 평가하는 표현을 쓰지 않는다.
5. 불필요한 감탄, 과한 칭찬, 막연한 위로를 넣지 않는다.
6. 과업 수행 중에는 정답, 성공 여부, 개선안, 예상 결과를 암시하지 않는다.

## 2. 외부 자료 검토 결과

### 2.1 W3C 인지 접근성 보조 지침

W3C의 인지 접근성 보조 지침은 쉬운 단어, 짧은 문장, 짧은 글 묶음, 모호하지 않은 표현을 권장한다. 여러 단계가 있는 활동은 각 단계를 빠뜨리지 않고 나누어, 활동 전에 또는 활동 가까이에 제공하는 방식도 권장한다.

이번 프로젝트에서는 이를 다음과 같이 적용했다.

- 서비스 소개와 과업 준비의 진행 방법을 번호 목록으로 변경
- 한 문장에 섞여 있던 조건과 행동을 두 문장으로 분리
- `실행`, `처리`, `해당`처럼 대상을 숨기는 표현을 구체적인 기능 이름으로 변경
- 상태 설명을 짧게 줄이고 같은 내용을 여러 영역에서 반복하지 않도록 정리

이 자료는 WCAG 적합성 판정에 직접 추가되는 성공 기준이 아니라, 인지 및 학습장애 사용자를 포함해 더 이해하기 쉬운 콘텐츠를 만들기 위한 보조 지침이다.

### 2.2 W3C 알림과 피드백 지침

W3C는 사용자가 상호작용 중 무슨 일이 일어났는지 알 수 있어야 하며, 오류 문구는 혼란을 주는 대신 해결 방법을 분명하게 알려야 한다고 설명한다.

이번 프로젝트에서는 다음과 같이 적용했다.

- 새 탭이 열리지 않은 사실과 팝업 허용이라는 다음 행동을 한 문장 묶음으로 제공
- 과업 수행 페이지가 닫혔을 때 다시 여는 방법을 함께 안내
- 시작 정보가 없을 때 내부 저장 구조를 설명하지 않고, 탭을 닫고 과업 요청이 있는 창에서 다시 열도록 안내
- 단순 성공·실패 문구보다 실제로 저장된 수행 상태를 설명

### 2.3 GOV.UK 오류 문구 지침

GOV.UK Design System은 오류에서 무엇이 잘못되었는지와 어떻게 고칠 수 있는지를 설명하고, 서비스 문제를 사용자의 잘못처럼 표현하지 않도록 안내한다.

이번 프로젝트에서는 `실패`, `잘못했습니다`, `수행 불가능`처럼 사람을 평가하는 표현을 제거했다. 대신 다음처럼 기록이나 화면 상태를 주어로 삼았다.

- `요청한 자료를 저장한 기록이 없습니다.`
- `요청한 시간 대신 다른 일정이 예약되었습니다.`
- `선택한 답이 미리보기 내용과 다릅니다.`

### 2.4 U.S. Web Design System의 사람 중심 문체

U.S. Web Design System은 복잡한 절차에서 사용자의 시간과 상황을 존중하고, 명확한 기대와 안내로 인지 부담과 좌절을 줄이는 방식을 강조한다.

이번 프로젝트에서는 친근함을 감탄사나 칭찬으로 표현하지 않았다. 대신 사용자가 중단하거나 다시 시작할 수 있는 선택을 차분하게 알리고, 각 버튼을 눌렀을 때 일어나는 일을 정확히 설명했다.

## 3. 적용한 문체 기준

### 3.1 명령형 완화

사용자 화면의 `~하십시오`, `~주십시오`, `~고르십시오`, `~누르십시오`를 문맥에 따라 `~하세요`, `~해 주세요`, `~누르세요`로 바꿨다.

과업 목표는 지나치게 구어적이거나 장황해지지 않도록 짧은 요청형 문장으로 유지했다.

예:

- 변경 전: `기존 예약을 하나 취소한 뒤 박하늘 상담사의 목요일 10:00 대면 30분 시간으로 새로 예약하십시오.`
- 변경 후: `기존 예약을 하나 취소한 뒤 박하늘 상담사의 목요일 10:00 대면 30분 일정을 새로 예약하세요.`

### 3.2 친근함과 테스트 중립성의 균형

다음 표현은 친근해 보일 수 있지만 이번 테스트에는 사용하지 않았다.

- `잘하셨습니다`
- `앗`, `이런`
- `걱정하지 마세요`
- 성공을 암시하는 축하 문구

이런 표현은 화면낭독기 발화를 늘리고, 사용자를 어린아이처럼 대하는 느낌을 줄 수 있으며, 과업 성공 여부에 대한 단서가 될 수도 있다. 따라서 따뜻함은 짧고 존중하는 문장, 선택권 안내, 비난하지 않는 오류 문구로 구현했다.

## 4. 화면별 주요 변경

### 4.1 홈 화면

- 첫 안내를 `먼저 테스트할 서비스 유형을 골라 주세요.`로 변경
- 서비스 버튼을 `예약 캘린더 테스트 시작`처럼 대상과 행동이 함께 드러나는 이름으로 통일
- `저장 상태`를 `진행 내용`으로 변경
- 서비스 진행 설명을 다음처럼 단순화
  - `아직 시작하지 않았습니다.`
  - `1개 과업을 마쳤습니다.`
  - `모든 과업을 마쳤습니다.`

### 4.2 서비스 소개 화면

- 첫 문단에서 실제로 하게 될 일만 설명하고 새 탭·요청 확인 안내의 반복을 줄임
- `진행 방법`을 `진행 순서`로 변경하고 번호 목록 사용
- `주의할 점`을 `알아두세요`로 변경
- 시작 버튼을 `첫 과업 준비하기`로 변경
- 돌아가기 버튼을 `다른 서비스 고르기`로 변경
- 과업을 완료하기 어려울 때 현재 상태를 저장하고 다음 단계로 갈 수 있음을 중립적으로 안내

### 4.3 과업 준비 화면

- `수행 준비`를 `과업 시작 준비`로 변경
- 진행 절차를 다섯 단계 번호 목록으로 정리
- 종료 확인 창의 두 버튼이 각각 무엇을 하는지 직접 설명
- 스위치 문구를 `과업 요청을 수행 페이지에도 표시`로 단순화
- 실행 영역 제목을 `과업 열기`로 변경
- 기록 시작 시점을 `처음 키를 누르거나 화면을 클릭하면`으로 구체화
- 새 탭 버튼을 `과업 수행 페이지 열기(새 탭)`으로 정리

### 4.4 상태와 오류

대표 변경은 다음과 같다.

- 변경 전: `새 탭을 열지 못했습니다. 팝업 차단을 해제한 뒤 다시 시도하십시오.`
- 변경 후: `새 탭이 열리지 않았습니다. 브라우저에서 이 사이트의 팝업을 허용한 뒤 다시 열어 주세요.`

- 변경 전: `과업 수행 페이지가 닫혔습니다. 필요하면 새 탭을 다시 열 수 있습니다.`
- 변경 후: `과업 수행 페이지가 닫혔습니다. 계속하려면 아래 버튼으로 다시 열어 주세요.`

- 변경 전: `수행에 필요한 시작 정보가 없습니다. 원래 테스트 창에서 과업을 다시 여십시오.`
- 변경 후: `과업을 시작하는 데 필요한 정보를 찾지 못했습니다. 이 탭을 닫고, 과업 요청이 있는 창에서 다시 열어 주세요.`

- 변경 전: `해당 기능은 현재 점검 중입니다. 이 화면 안에서 계속 진행하십시오.`
- 변경 후: `이 기능은 현재 준비 중입니다. 다른 기능은 이 화면에서 계속 이용할 수 있습니다.`

### 4.5 과업 종료와 수행 결과

- 종료 질문을 `현재 상태로 과업을 마칠까요?`로 변경
- 확인 문구에서 실제 버튼 이름을 그대로 사용
- 성공 결과를 `과업을 완료했습니다.`로 변경
- `수행 불가능 기록`을 `완료하지 못한 과업`으로 변경
- 사용자의 행동을 평가하는 대신 저장된 사실을 설명

대표 예:

- `요청한 상담 예약 시간과 다른 시간을 예약했습니다.` → `요청한 시간 대신 다른 일정이 예약되었습니다.`
- `기존 예약 취소가 완료되지 않았습니다.` → `기존 예약을 취소한 기록이 없습니다.`
- `요청한 댓글의 답글 목록에 진입하지 못했습니다.` → `요청한 댓글의 답글 목록을 연 기록이 없습니다.`
- `요청한 자료를 저장하지 못했습니다.` → `요청한 자료를 저장한 기록이 없습니다.`

### 4.6 결과 화면

성공을 전제로 하거나 내부 측정 용어처럼 보이는 제목을 정리했다.

- `과업 완료` → `과업 수행 기록`
- `실제 기록 요약` → `수행 기록 요약`
- `완료 시간` → `수행 시간`
- `숨김 탭 제외 시간` → `수행 페이지가 보이지 않았던 시간`
- `사전 계산 기준` → `사전 예상 기준`
- `왜 조작 부담 차이가 나는가` → `조작 부담이 달라지는 이유`
- `비교안 A/B 최종 비교` → `비교안 A와 B 결과 비교`
- `기록 확인 안내` → `결과를 볼 때 참고하세요`

결과 파일 설명은 먼저 파일이 필요한 상황을 알리고, JSON 형식 설명을 뒤에 두었다.

### 4.7 설문 연결 안내

- `설문지 제출 준비` → `테스트 마무리`
- `구글 설문지로 수행 기록 전달` → `테스트를 마치고 설문 작성하기`
- `구글 설문지로 이동` → `설문 작성하기(새 탭)`
- 완료 개수 표기를 `3개 중 2개 서비스 완료`처럼 읽기 쉽게 변경

자동 응답에 들어가는 기록 문장도 `완료 시간`, `수행 불가능` 대신 `수행 시간`, `완료하지 못한 과업`을 사용한다.

### 4.8 과업 요청 문장

세 서비스의 과업 요청은 정답이나 탐색 전략을 추가하지 않고 문장 구조만 정리했다.

- 긴 한 문장을 둘로 나눔
- 선택값에는 한국어 인용 부호 사용
- `시간`을 문맥에 맞게 `일정`으로 변경
- 검색 미리보기 답변 위치를 실제 제목인 `답변 선택`으로 안내

## 5. 테스트 타당성을 위해 유지한 제한

이번 문구 개선은 다음 내용을 바꾸지 않았다.

- A/B 무작위 순서
- 과업 목표와 정답
- 과업 수행 페이지의 탐색 구조 차이
- 기록 시작·종료 방식
- 사전 예상 계산식과 실제 로그 수집 방식
- 수행 중 성공 여부 비공개 원칙
- 설문 자동 입력 필드 구조

또한 과업 수행 전에는 예상 시간, 개선폭, 권장 탐색 순서, 어느 화면이 개선안인지 표시하지 않는다.

## 6. 문서와 자동 점검 보강

### 6.1 화면 문구 작성 가이드

`docs/language-guideline-wcag-3.1.3-kwcag.md`를 현재 화면 기준으로 다시 정리했다. 명확성, 존중하는 문체, 상태·오류 작성법, 테스트 편향 방지, 현재 용어, 화면별 규칙, 배포 전 점검 항목을 포함한다.

### 6.2 수동 점검표

`docs/manual-release-checklist.md`에 다음 항목을 추가하거나 갱신했다.

- 진행 단계가 번호 목록인지
- 상태와 오류에 다음 행동이 있는지
- 사용자를 탓하는 표현이 없는지
- 불필요한 감탄이나 과한 격려가 없는지
- 같은 안내가 반복되지 않는지
- 현재 버튼·제목·결과 용어가 일관되는지

### 6.3 문구 회귀 검사

`scripts/check-user-facing-copy.mjs`를 추가했다. 이 스크립트는 다음을 자동 확인한다.

- 삭제한 딱딱한 문구가 다시 들어오지 않았는지
- 현재 핵심 문구가 유지되는지
- 불필요한 감탄과 과한 격려가 없는지
- 사용자를 탓하는 문구가 없는지

이 검사는 `npm run check`와 `npm run smoke`에 포함된다.

## 7. 검증 결과

다음 검사를 실행해 통과했다.

```bash
node --check app.js
node --check comments-app.js
node --check search-app.js
node --check lib/service-shell.js
node --check lib/survey-link.js
node --check lib/utils.js
node scripts/check-user-facing-copy.mjs
npm run benchmark
npm run check
```

`npm run check`에는 정적 품질 검사, 공통 UI 계약 검사, 서비스별 상태 저장 검사, 무작위 답변 연동 검사, 과업 수행 페이지 렌더링 검사, 새 문구 회귀 검사가 포함된다.

## 8. 남은 수동 확인

자동 검사로 문구 존재 여부와 주요 렌더링 흐름은 확인했지만, 다음 항목은 실제 브라우저와 보조기술에서 수동 확인해야 한다.

- NVDA, JAWS, VoiceOver, TalkBack에서 문장이 자연스럽게 끊겨 읽히는지
- 상태 메시지가 지나치게 자주 또는 중복으로 읽히지 않는지
- 번호 목록과 버튼 이름만으로 다음 행동을 이해할 수 있는지
- 오류 상황에서 안내한 다음 행동이 실제 브라우저 설정과 맞는지
- 친근한 문체가 특정 연령이나 장애 사용자를 어린아이처럼 대하는 느낌을 주지 않는지
